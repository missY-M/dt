# 第一部分实验说明

## 1. 本阶段研究问题

在没有云端兜底的异构边缘环境中，一个复杂请求由若干预先定义、可以并行执行、不可再拆分的子任务组成。每个子任务需要分配给一个具有对应能力的边缘节点；同类子任务可能有多个候选节点，各节点的质量、计算效率、内存和网络条件不同。

本阶段回答：在静态画像准确、没有状态陈旧和模型能力漂移的条件下，如何根据需求和能力筛选候选节点，并结合共享网络与排队状态完成分配，使更多请求满足质量门槛和截止时间？

这里的“通用模型”按黑盒能力处理：只使用任务类型、输入类别、画像质量和计算量系数等外部描述，不依赖某个模型的内部层结构。默认每节点每任务类型只配置一个模型，本轮重点是节点选择，不同时研究模型库选择。

## 2. 老师要求与实现选择

| 内容 | 依据及本轮处理 |
|---|---|
| 通用任务/模型黑盒 | 对应老师要求；使用外部能力参数，不切模型层、不训练模型 |
| DT 能力画像及主动推荐 | 对应老师要求；本轮画像静态且准确，根据需求输出候选推荐分数 |
| KDN 协调分配 | 对应老师要求；本轮采用已到达请求批内的近似联合分配 |
| 纯仿真实验 | 对应老师允许的实验方式；使用 EdgeSimPy |
| 画像匹配与基础调度先完成 | 用户已确认的第一部分范围 |
| 6 节点、2 类型、120 请求、5 种子、3 负载 | 本次建议的起步规模，不是老师指定参数 |
| 所有算力、内存、带宽、质量、计算量数值 | 合成实验参数，没有真实硬件或模型测量依据 |
| 匹配权重、搜索宽度、tick | 实现超参数，正式论文需做敏感性分析 |
| 信息年龄、双新鲜度、模型漂移与重调度 | 后续部分，本轮不声称已经实现 |

本阶段的 DT 是静态能力画像和推荐接口。它没有在线同步机制、预测模型或状态信息年龄。论文应把这一点作为受控实验条件说明，避免将它写成已经完成完整动态数字孪生系统。

## 3. 场景与数据

### 3.1 默认场景

配置文件为 `config/default.json`。默认 6 个虚拟边缘节点，2 类子任务分别标记为 `image_classification` 与 `object_detection`。每个复杂请求包含每类恰好一个子任务，它们可以并行分配；所有结果返回后进行一次汇聚。

节点有不同算力、可用执行内存、接入带宽、链路传播时延和静态模型能力。所有节点通过同一个骨干链路连接请求端，共享链路会产生竞争。每个节点**同时只执行一个任务**，但允许多个任务排队；同一个节点可以服务多个请求，不能把单执行槽理解为节点在整个实验中只能接一个任务。

### 3.2 这次用的是什么数据集

本轮没有使用 ImageNet、COCO 等真实图片数据集。数据由 `scenario.py` 按固定种子生成，是可保存、可重放的**合成任务轨迹**。分类/检测仅给任务类型提供具体例子，`easy`/`hard` 是输入条件标签，没有读取真实图像或运行推理模型。

到达间隔服从指数分布，形成给定到达率的泊松到达过程。每个请求的输入类别、质量门槛、计算量、输入数据量和截止时间预算在轨迹生成时确定，调度时不再随机采样。第一条请求也等待一个指数分布到达间隔。

同一个负载和种子下，所有方法复用同一请求轨迹。质量画像固定，环境配置相同。不得把合成质量参数报告为真实模型准确率，也不得把单次请求的 `qos_ok` 解读为模型输出事实正确。

## 4. 需求画像与节点能力画像

### 4.1 子任务需求

| 字段 | 含义 |
|---|---|
| `task_type` | 子任务类型 |
| `input_class` | 输入条件类别 |
| `min_quality` | 最低统计能力质量门槛 |
| `work_gflop` | 基础计算量，GFLOP |
| `memory_mb` | 执行期间占用的内存，MB |
| `input_mb` / `output_mb` | 输入/输出数据量，MB |

请求层定义 `arrival_s`、绝对截止时刻 `deadline_s`、汇聚耗时 `aggregation_s`。配置中的 `request_deadline_s_range` 是相对到达时刻的时间预算；生成轨迹后 `deadline_s=arrival_s+预算`。这里的时延需求是上限，不能写成“任务要求最小时延”。

### 4.2 节点能力

| 字段 | 含义 |
|---|---|
| `cpu_gflops` | 节点执行算力，GFLOP/s |
| `memory_mb` | 扣除常驻模型后可用于任务执行的内存 |
| `bandwidth_mb_s` / `latency_s` | 节点接入链路带宽和单向传播时延 |
| `model_id` / `task_type` | 模型标识及支持的任务类型 |
| `quality_by_input` | 不同输入类别下的合成统计质量能力 |
| `compute_factor` | 该模型相对基础计算量的系数 |

单位统一为秒、GFLOP、GFLOP/s、十进制 MB 和 MB/s，其中 1 MB = 1,000,000 字节。执行耗时近似为 `work_gflop × compute_factor / cpu_gflops`，再向上对齐仿真 tick。

执行时才占用任务内存，CPU 完成后释放。排队中的输入被抽象为不占该执行内存池，模型常驻内存已经从节点容量中扣除；本轮没有模拟输入缓冲区、模型加载或磁盘缓存。

## 5. DT 主动推荐与画像匹配

### 5.1 先做硬兼容筛选

所有方法都检查：节点支持相同任务类型；能力画像包含该输入类别；节点执行内存足够。只有 `qos_greedy` 和 `global_beam` 额外把质量达标和预计请求截止时间作为接纳硬约束。

因此，简单基线可以执行类型兼容、内存可行但质量不达标或预计超时的任务，最终按统一指标计为 QoS 失败。基线拥有相同画像信息，只是采用不同的决策规则。

### 5.2 同含义的需求与能力向量

对当前子任务和候选节点，需求向量组织为：

```text
d = [最低质量 q_min, 剩余时间预算 B, 执行内存需求 M_req]
c = [画像质量 q, 预计返回加汇聚耗时 T_hat, 可用执行内存 M_avail]
```

按方向和量纲归一化的裕量为：

```text
s_q = clip((q - q_min) / max(1 - q_min, ε), 0, 1)
s_t = clip(1 - T_hat / max(B, ε), 0, 1)
s_m = clip(1 - M_req / max(M_avail, ε), 0, 1)
S   = (w_q*s_q + w_t*s_t + w_m*s_m) / (w_q + w_t + w_m)
```

默认 `(w_q, w_t, w_m)=(0.5, 0.4, 0.1)`。权重非负且至少一项为正。质量恰好过门槛时质量裕量为 0，依然可以接纳；分数为 0 不等于不可行。

本轮 `M_avail` 使用节点配置的可用执行内存容量，不减去当前正在执行任务的临时占用，因为新任务可以排队等待，而节点一次只执行一个任务。不能把这个分数解释成并发执行情况下的瞬时空闲内存匹配。

推荐分数在 `[0,1]`，表示满足需求后还剩多少裕量。时延越低越好；不能直接把秒、MB 和质量数值拼接后计算未归一化距离。本轮使用结构化向量与硬字段匹配，没有自然语言语义编码器，也不应把余弦相似度或简单加权本身称作已经证明的学术创新。

## 6. KDN 基础分配

### 6.1 完成时间预测

`planner.py` 根据当前可观测的执行队尾、输入/输出大小、模型计算量系数、节点算力和网络参数预测返回时刻。共享带宽用当前活跃流和本批候选任务数做近似等分；实际执行时由 EdgeSimPy 动态共享网络。

同一节点的任务串行预约 CPU 队尾，输出返回不占执行槽。完整请求的预计结束时刻为最晚子任务预计返回时刻加汇聚耗时。

预测不读取未来请求，也不能保证真实截止时间。后来到达的流、共享网络变化和 FIFO 队头阻塞都可能造成偏差。`tasks.csv` 同时保存 `predicted_return_s` 与 `returned_s`；预计过门槛不能直接当成最终完成成功。

### 6.2 五种方法

| 方法 | 主要作用 |
|---|---|
| `round_robin` | 只按基础兼容条件轮询，提供简单分配参照 |
| `earliest_finish` | 逐子任务选预计返回最早者，观察单独追求时延的表现 |
| `quality_first` | 逐子任务优先质量，观察单独追求质量的表现 |
| `qos_greedy` | 加入质量/时限过滤和推荐分数，仍然逐子任务贪心 |
| `global_beam` | 同请求子任务联合放置，并在同管理 tick 的已到达请求批次中进行有限宽度联合搜索 |

`qos_greedy` 的选择代价使用归一化预计时延减去 `matching_weight × S`，默认 `matching_weight=0.15`。它接受前面子任务的贪心选择，后续选择可能因此失去可行位置。`qos_greedy` 与 `global_beam` 都按 `(deadline_s, request_id)` 排序同批请求，避免把请求顺序差异混入搜索方式的对比。

`global_beam` 枚举每个请求的子任务联合放置，保留请求拒绝分支。请求按截止时刻排序，搜索状态包含已经接纳的请求数、累计代价、节点 CPU 预约队尾和分配计划。字典序目标先最大化当前批接纳数，再最小化累计代价；每个完整请求的代价为“归一化预计请求时延 − `matching_weight × 子任务 DT 推荐分数均值`”，不能简化成只最小时延。每轮保留默认 32 个状态。

beam 宽度有限，请求处理顺序固定，带宽预测也近似，因此它不是全局最优算法。“全局”仅表示当前可见请求批内的跨节点协调，不表示看到整条未来轨迹或求解无限时间优化问题。

默认 `tick_s=0.01`，泊松到达率最高 2 请求/秒，大多数管理批次只有一个请求。因此默认实验主要检验同请求子任务联合分配，跨请求批内协调的作用需要用同步/突发到达轨迹额外验证。不能仅凭默认标准实验宣称已经充分验证跨请求的全局协调收益。

请求整体接纳或整体拒绝：任何子任务没有可行分配时，不提交此前子任务的预约，也不发送部分输入。

## 7. EdgeSimPy 与本项目扩展的分工

### 7.1 使用的官方能力

本项目使用官方 `Simulator` 推进 tick，使用 `EdgeServer` 表示边缘节点，使用 `NetworkSwitch`、`NetworkLink`、`NetworkFlow` 表示拓扑和真实共享传输。图为无向图，同一物理链路的输入和输出方向共享容量。

拓扑为 `请求端交换机 → 核心交换机 → 节点交换机`。所有输入和结果返回都经过同一骨干链路；每个节点还有独立接入链路。默认公平分配按链路计算份额，端到端流用路径瓶颈份额推进，不将其描述成多跳网络的全局最优资源分配。

官方 `NetworkFlow` 每 tick 直接减去分得的带宽，没有自动乘 `tick_duration`。适配层将 `MB/s × tick_s` 转换为 MB/tick 后写入链路容量。官方 flow 也没有自动计入 `NetworkLink.delay`，本项目在流传完后补上路径传播时延并向上对齐 tick。

### 7.2 本项目实现的机制

`engine.py` 扩展了任务级 FIFO、单执行槽、执行内存占用和释放、结果返回、请求汇聚、请求接纳和拒绝、排空截止以及容量审计。

CPU 队列按接纳顺序 FIFO。已经排到队头但输入尚未传完的任务会阻塞后面的任务，后到的小任务不能越过队头。这个规则与模型冷启动、GPU 并行或可抢占调度无关，后续若研究它们需要显式扩展。

在每个 tick 边界，管理回调先结算已经发生的网络和计算事件，处理结果汇聚和新到达请求，再启动可执行的队头。随后官方调度器进行网络带宽分配并推进传输。输入不能在尚未传完时开始计算，输出也只能在计算完成后开始传输。

网络传输完成后，传播事件可能已经有确定的未来时刻，因此需要区分 `returned_s` 与任务最终状态；完成请求使用所有子任务实际返回时刻的最大值加汇聚耗时。

EdgeSimPy 使用全局组件表，因此同一进程中的实验顺序运行并在每次初始化时清空。不要用多线程交错运行多个实验实例；如需并行，应采用独立进程。

官方依据：[Simulator](https://github.com/EdgeSimPy/EdgeSimPy/blob/76eb5ead74596bb4240759fa4336f1d6f190c70a/edge_sim_py/simulator.py)、[NetworkFlow](https://github.com/EdgeSimPy/EdgeSimPy/blob/76eb5ead74596bb4240759fa4336f1d6f190c70a/edge_sim_py/components/network_flow.py)、[默认公平分配](https://github.com/EdgeSimPy/EdgeSimPy/blob/76eb5ead74596bb4240759fa4336f1d6f190c70a/edge_sim_py/components/flow_scheduling/max_min_fairness.py)。

## 8. 指标定义和读图要求

### 8.1 请求级 QoS

一个请求满足 QoS，要求它已经完成，且同时满足：

```text
所有子任务的被选模型画像质量 >= 各自 min_quality
ceil_to_tick(max(所有子任务 returned_s) + aggregation_s) <= deadline_s
```

这不是把两个子任务质量相乘得到最终准确率，也不是采样两个独立正确/错误结果。它仅表示统计能力门槛与请求级时限同时满足。

### 8.2 汇总指标

| 指标 | 分子与分母/解释 |
|---|---|
| `qos_success_rate` | 满足上述 QoS 的请求数 / 全部请求数 |
| `rejection_rate` | 拒绝请求数 / 全部请求数 |
| `unfinished_rate` | 排空上限仍未完成请求数 / 全部请求数 |
| `timeout_rate` | （已完成但超时的请求数 + 排空截断且已超截止的未完成请求数）/ 全部请求数；不含拒绝 |
| `quality_failure_rate` | 已完成但画像质量不达门槛的请求数 / 全部请求数 |
| `mean_completed_latency_s` | 所有已完成请求时延均值，包括超时/质量失败样本 |
| `p95_completed_latency_s` | 每次运行所有已完成请求的时延 P95 |
| `mean_cpu_utilization` | 各节点执行忙时 / 该次总仿真时长，再对节点平均 |
| `mean_scheduler_wall_ms` | 每个有新请求管理批次的调度墙钟耗时均值 |
| `wall_runtime_s` | Python 运行该次仿真的真实耗时，不是请求仿真时延 |

超时和质量失败可重叠，排空截断的未完成样本也计入超时率，因此不能把这些故障率与拒绝率简单相加。所有拒绝和未完成样本仍保留在 QoS 分母中；没有已完成请求时，完成时延留空，不填 0。

必须将完成时延与拒绝率、未完成率和 QoS 一起读。更低的已完成样本时延，可能来自拒绝困难请求，不能单独证明方法更好。

`summary.csv` 对相同负载和方法的每种子指标求均值及样本标准差。P95 汇总是“每种子 P95 的均值”，不是合并所有种子后重算的总体 P95。图中误差棒是样本标准差，不是置信区间；有效种子不足两个时标准差为空。


标准默认为 120 请求 × 5 种子 × 3 到达率 × 5 方法，其中独立仿真运行数为 `5×3×5=75`，120 是每次运行的请求数量。默认输出带时间戳的新目录，非空输出目录不覆盖。

`requests.csv` 包含所有请求；`tasks.csv` 只包含已经接纳的子任务，拒绝请求没有真实派发的子任务时间线；`nodes.csv` 是节点运行摘要。容量审计检查每拍网络分配不超过链路容量，执行开始时检查内存不超节点容量。测试用于核对机制与边界，不代替论文对比实验。

本说明不预先填写收益百分比或假定某方法一定最好。任何结论必须来自实际运行结果，并结合拒绝、截断、预测误差和多种子波动解释。

## 10. 正式论文还需要补齐什么

本轮五方法是机制原型与消融式参照，没有完整复现老师的 HCIO、CAO 或其他文献算法。正式对比应进一步挑选与“黑盒子任务分配”假设相符的近年方法，说明改动和适配，不能只沿用论文名称。

需要补充节点/模型/任务参数来源，或通过真实模型 profiling 与公开轨迹校准参数。还需检验任务规模、节点规模、请求负载、内存约束、质量门槛、匹配权重、`matching_weight`、beam 宽度及时间粒度的敏感性，并单独验证突发批次下的联合分配。

后续状态新鲜度实验要显式区分真实状态与调度器看到的 DT 状态；模型能力变化实验要显式生成能力随输入分布或模型变化的过程。本轮两者相同且静态，不能从本轮结果推导双新鲜度方法已经有效。
