## 1. 先看程序怎样串起来

整个程序做的是：对已定义好子任务的复杂请求，依据需求、节点能力及当前状态分配节点；在 EdgeSimPy 中执行；记录实际仿真结果并统计。

```text
run.py 的 main()
  → load_config()：读取并检查配置
  → nodes_from_config()：构造节点和模型能力画像
  → generate_requests() 或 load_trace()：得到固定请求轨迹
  → 对每种方法构造 Experiment
      → Experiment.run() 推进 Simulator 时钟
          → Experiment._manage() 处理每个tick的事件
              → Planner.plan_batch() 给当前已到达请求作分配
                  → compatible() 筛候选
                  → estimate() 预测返回时间
                  → _score() → recommend() 计算匹配分数
              → 执行接纳/拒绝方案，创建传输、入队、执行和返回
          → _audit_tick() 检查容量并统计忙时
      → 返回请求、子任务、节点记录和计时/审计摘要
  → summarize()：单次运行指标
  → write_csv()：写明细和指标
  → aggregate()：跨种子汇总
  → draw()：绘制比较图

validate_results.py 的 main()
  → 另行读取已经导出的结果，核查一致性，写 validation.json
```

固定请求轨迹里虽然保存了后续请求，调度器只接收本时刻已经到达的请求。真实队列和网络传输会持续变化；没有把未来轨迹交给算法预先安排。

## 5. matching.py：把需求和能力转成推荐分数

文件：`/home/sanyue/edge-infer-task/stage1/matching.py`。

| 函数 / 行号 | 输入 | 返回值 | 作用和边界 |
|---|---|---|---|
| `recommend(...)` / 20 | 最低质量、画像质量、剩余时间预算、预计耗时、内存需求、执行容量、三个权重 | `DTRecommendation` | 纯计算，返回两个向量、三维裕量和综合分数；不写文件、不改队列，也不自行拒绝不合格节点 |
| 局部 `clip(x)` / 29 | 一个数 | 限制到0～1的数 | `recommend` 内的 lambda，处理裕量截断，不是独立对外接口 |

`recommend` 的完整参数顺序是：`min_quality, quality, time_budget_s, predicted_latency_s, required_memory_mb, available_memory_mb, weights=(0.5,0.4,0.1)`。

```text
s_q = clip((quality - min_quality) / max(1 - min_quality, 1e-9))
s_t = clip(1 - predicted_latency_s / max(time_budget_s, 1e-9))
s_m = clip(1 - required_memory_mb / max(available_memory_mb, 1e-9))
score = Σ(权重 × 对应裕量) / Σ权重
```

权重必须恰好三个、有限非负、总和大于0，否则报错。质量和时限的硬筛选由 Planner 的两个 QoS 方法负责，不能用分数裁剪替代可行性检查。分数0不一定不可行，分数也不是模型准确率或最终成功概率。

时间由 Planner 先预测，再传入该函数；`recommend` 自身不预测时间。当前传入的预计耗时为“预计子任务返回时刻＋汇聚耗时－当前时刻”，内存取节点执行容量而非瞬时空闲内存。

| `Planner.plan_batch(requests, ready, now, active_flows=0)` / 120 | 本批已到达请求、CPU队尾表、当前时刻、活跃流数 | `tuple[RequestPlan, ...]` | 总决策入口；空批返回空元组；轮询更新游标，其余预约在局部字典中完成，不直接改真实队列或发网络流 |

`ready` 不是实际CPU队列本身，而是“各节点预计什么时候能接着执行新任务”的时间表。输入时刻、预测时刻均使用秒。

预测的主要计算是：

```text
share = max(1, 当前活跃流数 + 本批全部子任务数)
估计带宽 = min(节点接入带宽, 骨干带宽) / share
输入就绪 = 对齐(now + 输入大小/估计带宽 + 路径传播)
CPU结束 = 对齐(max(已预约队尾, 输入就绪) + 对齐后计算耗时)
结果返回 = 对齐(CPU结束 + 输出大小/估计带宽 + 路径传播)
```

这里按固定份数近似共享带宽，不是实际网络分配的严格下界；本批后来被拒绝的任务也可能已计入份数。未来传输未知，当前近似也有误差，所以估计按期不保证最终按期。

请求整体接纳或拒绝。某子任务失败时，不提交此前的局部CPU预约，也不实际派发部分任务。轮询游标是另一个状态，尝试选择时可能递增，不随整请求失败回退。

拒绝原因包括：`no_compatible_capacity`、`no_quality_candidate`、`predicted_deadline`、`joint_deadline_or_search_limit`；beam 中还可能保留 `batch_admission_tradeoff`，表示为批次接纳权衡而拒绝。

### 7.1 `_manage` 的事件顺序

1. 收集网络流完成信息，等待传播后的实际就绪/返回时刻到达。
2. 已完成CPU任务释放执行内存和运行槽，创建输出传输。
3. 所有结果都返回且汇聚时刻已到，记录完整请求完成及QoS。
4. 仅释放 `arrival_s<=now` 的请求，交给 Planner 作本轮决策。
5. 拒绝时记录结果；接受时创建任务状态、入FIFO队列并发起输入传输。
6. CPU空闲时只看队头。队头输入不齐，后面的任务即使输入齐也不能越过。

CPU完成后，输出网络传输可以与下一任务计算重叠。任务执行期间占用执行内存，计算结束释放；排队输入缓冲不占该内存池。模型常驻内存已经从节点配置容量中扣除，不模拟模型加载。

### 7.2 运行上限与返回结果

```text
latest = 全部请求绝对截止时刻的最大值；空轨迹时为0
limit = latest + max_drain_s
max_steps = ceil(limit/tick_s) + 1
```

默认120秒排空余量是从最大请求截止时刻之后计，不是实验总共只运行120秒，也不是从最后到达时刻开始计。若全部请求已经完成或拒绝，会提前结束。达到上限仍未完成的请求保留为 `unfinished`，并保留当时资源占用。

`run()` 返回以下字段：

| 字段 | 含义 |
|---|---|
| `requests` | 所有请求结果，包含拒绝和未完成 |
| `tasks` | 仅已接纳子任务记录；被拒绝请求没有实际派发的任务明细 |
| `nodes` | 每节点接纳数、CPU忙时/利用率和执行内存峰值 |
| `simulation_duration_s` | 最终仿真时间点 |
| `wall_runtime_s` | `run()` 在电脑上实际耗时，不含构造环境、导出和画图 |
| `scheduler_wall_s` | 各有新请求批次的队尾估计及Planner调用耗时之和 |
| `decision_count` | 有新请求的决策批次数，不是子任务数 |
| `max_network_capacity_ratio` | 运行中最大链路分配量/容量比 |
| `network_flow_count` | 累计创建的流数，含已结束的流 |
| `residual_execution_memory_mb` | 停止时仍占用的执行内存 |

调度墙钟开销没有加到仿真请求时延。EdgeSimPy 有全局组件表，不适合同进程多线程交错运行多个实例；当前实验顺序执行。

主要统计定义：

```text

```

## 12. 基线是什么，五种方法分别比较什么

“基线”是用来判断待研究方法是否有改进的参照方法。当前共有5个对比方案：前三个是基础规则，QoS贪心是较直接的参照，联合搜索是待验证的联合方案。

| 方法 | 决策规则 | 质量硬门槛 | 预计截止硬门槛 | 决策使用匹配分数 | 主要用途 |
|---|---|---|---|---|---|
| `round_robin` | 在基本兼容候选之间轮着选 | 否 | 否 | 否 | 基础参照 |
| `earliest_finish` | 每子任务选预测返回最早者，同值按节点ID | 否 | 否 | 否 | 观察只追求速度的影响 |
| `quality_first` | 优先最高画像质量，再比预测时间与节点ID | 否 | 否 | 否 | 观察优先质量的影响 |
| `qos_greedy` | 质量/预计时限过滤后，逐子任务按时延减匹配奖励选 | 是 | 是 | 是 | 最直接的贪心参照 |
| `global_beam` | 同请求组合枚举与同批请求有限搜索 | 是 | 是 | 是 | 检验联合分配是否有增量价值 |

所有方法共用类型、输入类别、内存兼容条件，能看到相同画像、轨迹和初始环境。前三种也会计算和记录匹配分数，但选择规则不使用它；不能把结果差异解释成前三种没有质量信息。

两个QoS方法采用相同批内 `(deadline_s, request_id)` 排序、质量/预计时限条件和评分函数，因此两者是判断“联合搜索相对逐任务选择”更直接的一组比较。

联合搜索保留接受与拒绝分支，先最大化本批接纳数，再最小化累计：

```text
预计完整请求时延/请求总时间预算
− 0.15×各子任务匹配分数均值
```

默认只保留32个状态，请求处理顺序固定；没有全局最优保证。默认tick和泊松负载下，多数批次只有一个请求，因此跨请求协调需另外用突发/同步轨迹检验。

当前5种方法不是HCIO、CAO、PRAS或其他论文算法的完整复现，也没有单独隔离“有/无推荐评分”影响的完整消融。正式论文仍需选择假设相符的文献基线并说明适配，不能直接沿用文献名称。
